# 2. Build the Clojure client on clj-grpc and the shared core

## Status

Proposed

## Context

We want a client that Clojure applications use idiomatically: data in, data out, no Java builders.

We own the Clojure protobuf and gRPC stack:

- [protoc-gen-clojure](https://github.com/bpalermo/protoc-gen-clojure) generates a record per message and supports Edition 2024, which the Odradek protos use.
- [clj-protobuf](https://github.com/bpalermo/clj-protobuf) is its runtime and encodes records and maps to protobuf bytes.
- [clj-grpc](https://github.com/bpalermo/clj-grpc) is a gRPC runtime on unshaded Netty with Unix domain socket support, the same transport choices as the Odradek server.
- [rules_clj](https://github.com/bpalermo/rules_clj) builds Clojure under Bazel, which this repository uses.

The design makes a topic's contract a protobuf message type. A Clojure application therefore already needs clj-protobuf to build its payloads.

Three approaches were considered:

1. A thin wrapper over the finished Java client. Least work, but the application then carries grpc-java stubs and protobuf-java generated classes for the API, and our Clojure stack plays no part.
2. A pure Clojure implementation, including the protocol logic. Most idiomatic internally, but a third copy of the logic [ADR 1](0001-shared-client-protocol-core.md) exists to avoid duplicating.
3. The shared Java core for the protocol, with clj-grpc as the transport and generated Clojure namespaces for the API messages.

## Decision

We will build the Clojure client on the shared protocol core, clj-grpc and clj-protobuf (approach 3).

- API messages come from namespaces generated by protoc-gen-clojure from the Odradek API proto.
- clj-grpc carries the two streams over the Unix domain socket.
- The protocol logic is the Java core from ADR 1, called through interop and not exposed to applications.
- Applications pass records or maps for keys and values. The client encodes them with clj-protobuf as the topic's contract type.
- The client is built and tested with rules_clj in this repository and published to Clojars.

## Consequences

Clojure applications get a data-oriented API and one protobuf stack for both their payloads and the client.

Odradek becomes a real consumer of clj-grpc's client side: long-lived bidirectional streams over a Unix socket, with reconnects. Gaps found there are fixed in clj-grpc, which we can do because we own it, but the work lands on that project's schedule.

The repository gains a second way of resolving JVM dependencies. rules_clj resolves from `deps.edn`; the Java code resolves from the Maven lock. clj-grpc brings grpc-java and Netty, and they must match the versions pinned here, or one class path holds two copies. This has to be solved before the client can be built and is the main technical risk of this decision.

The core's interface is consumed from Clojure as well as Java, so it should use plain Java types that are comfortable through interop.

The Clojure client cannot start before the core exists.
