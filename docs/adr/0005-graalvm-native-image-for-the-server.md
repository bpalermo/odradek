# 5. Build a GraalVM native image of the server

## Status

Proposed

## Context

The server runs as a sidecar: one instance per application pod. Two costs of a JVM are therefore paid once per pod, not once per service.

- **Memory.** A JVM carries a baseline of heap, metaspace and code cache that a small pod's sidecar budget has to cover before the server does any work.
- **Startup.** The server is a native sidecar, so the application container starts only after the server's startup probe passes. JVM start and warm-up add to every pod start and every scale-up.

A GraalVM native image compiles the server ahead of time into one executable that starts in a fraction of the time and uses less memory at rest.

Native image works under a closed-world assumption: every class that can run is known at build time, and reflection, resources and JNI must be declared. Several parts of the server push against that.

- **Codec extensions.** The design loads serializer, deserializer and transform classes by name from jars in a directory at startup. A native image cannot load classes that were not compiled into it.
- **Kafka clients.** They instantiate classes named in configuration by reflection and load compression codecs through JNI.
- **Netty epoll.** The Unix domain socket transport is a JNI library.
- **protovalidate.** Configuration rules are CEL expressions evaluated at run time.

The build also changes. GraalVM does not cross-compile, so the arm64 executable has to be built on an arm64 machine; today both architectures of the image are built on one amd64 runner. The freely licensed GraalVM distribution offers only a serial garbage collector and no profile-guided optimisation, so its peak throughput is expected to be below the JVM's.

## Decision

We will build a GraalVM native image of the server in the regular build, next to the JVM build, and publish it as a second image variant.

- The JVM image remains the default and the reference. It is the only variant that loads extension jars from a directory.
- The native variant is published under the same repository with a `-native` tag suffix, for linux/amd64 and linux/arm64, signed like the JVM image.
- The native executable is built by Bazel from the same server library as the JVM binary, with the GraalVM toolchain pinned like every other toolchain.
- A native image contains exactly the codec classes compiled into it. Someone who needs their own serializer or transform in a native image builds one that includes those classes; the build exposes a way to do that.
- A configuration that names a class the native image does not contain is rejected at load, as any unloadable class is today.
- Reflection, resource and JNI metadata is kept in the repository and checked by tests, not regenerated by hand before a release.
- The end-to-end suite runs against both variants. A test that passes on the JVM and fails on the native image fails the build.
- arm64 native builds run on an arm64 runner.

## Consequences

Pods that use the native variant start sooner and reserve less memory for the sidecar. The size of the gain is unmeasured; we will publish startup time and resident memory for both variants once the server does real work.

The server now has two run-time behaviours to keep equal. Any dependency that uses reflection can work on the JVM and fail in the native image, in a code path that only runs in production. The end-to-end suite on both variants is the defence, and it is only as good as its coverage.

The codec extension model splits. On the JVM, extensions are jars dropped into a directory. In a native image they are a build-time input, and adopting an extension means building and operating one's own image. Users who rely on extensions will mostly stay on the JVM variant, which is the variant that benefits least from this decision.

Adding or upgrading a dependency gains a step: checking that it still works in a native image, and updating metadata when it does not. Kafka client upgrades are the likely source of this work.

Builds get slower and need more memory, and CI needs an arm64 runner. The publish workflow produces two variants, each for two architectures.

Peak throughput of the native variant may be lower than the JVM's under sustained load. For a sidecar whose latency is dominated by broker acknowledgements this is expected to be acceptable, but it is an assumption until measured. If it is wrong, the native variant stays the choice for small or bursty workloads and the JVM variant for heavy ones.

If the native variant cannot be kept passing the end-to-end suite at reasonable cost, it is dropped by a record superseding this one. The JVM variant does not depend on it.
